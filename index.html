CH 01

The Mental Model — How to Think About Agents

1.1 You Are the Senior — the Agent Is the Talented Junior

The right way to think about your relationship with Copilot, Claude Code, or any other coding agent is like working with a highly skilled assistant who has access to tools — but lacks independent engineering judgment. You define the problem, the constraints, and what "correct" looks like. The agent proposes solutions, writes initial code, explores logs and codebases, and delivers raw material for you to process and validate.

Key Principle

Engineers at leading organizations keep design decisions and complex judgment calls for themselves, delegating the "work around the work" to agents.

This division of labor is not about the agent's capability ceiling — it's about engineering accountability. The agent may be fast and impressively fluent, but it does not understand organizational context, long-term trade-offs, or downstream consequences. That responsibility stays with you.

1.2 Three Industry Trends in Agentic Coding

Research on how engineers in high-performing organizations use coding agents has identified three consistent patterns:

The "Work Around the Work" Trend

Most agent-assisted tasks are not core product development. They are log parsing, report generation, run comparison, small scripting — what's often called "glue work" or "meta-work." This is where agents deliver the most value, because these tasks would otherwise remain manual or simply not get done.

Engineers Reserve Design Decisions

When a task requires architectural thinking, understanding complex trade-offs, or decisions that affect system structure — engineers prefer to do it themselves. The agent is an execution tool, not a decision-making tool.

Automation of Previously Manual Work

Processes that were entirely manual — for example, non-engineers building their own tooling — now get automated because agents lower the entry barrier. People without deep engineering backgrounds can build things that previously required a developer.

1.3 What Agents Excel At — and Where They Fall Short

Agents Excel At

  • Parsing logs and complex data — scanning thousands of lines for patterns
  • Generating summaries, reports, and structured comparisons
  • Exploring and explaining unfamiliar codebases
  • Writing boilerplate, tests, and glue code
  • Initial debugging — forming hypotheses on root causes

Agents Fall Short On

  • Design and architecture decisions — lacking business context and long-term awareness
  • Critical edge cases only domain experts would recognize
  • Logic that cannot be quickly verified — high-risk without validation
  • Anything requiring organizational or stakeholder judgment
CH 02

The Basic Workflow — The Vibe Loop

2.1 The Five-Step Loop

Every productive agent interaction — whether you are a data scientist or a backend engineer — follows the same loop:

1
Define
Narrow the task
2
Explore
Let agent work
3
Validate
Verify output
4
Refine
Iterative feedback
5
Automate
Repeat → script

Step 1 — Define

This is the most important step. The narrower and more specific your task definition, the better the output. Instead of analyze the logs, write:

Parse the routing failure log. Focus on congestion metrics in
layers M5–M7, and list the top 3 possible root causes with
evidence from the log.

A vague prompt forces the agent to guess your intent. A precise prompt makes it work efficiently.

Step 2 — Explore

Let the agent work without interruption. Give it space to search, analyze, propose, and explain. Resist the urge to correct mid-flight — wait for the first draft before steering.

Step 3 — Validate

This is the step that separates professional from amateur use. Run the generated code, test edge cases, compare with expected behavior, and apply deterministic checks. Agents sometimes fabricate plausible-sounding logic — validation is non-negotiable.

Step 4 — Refine

After validation, return to the agent with structured feedback: "What assumptions did you make?", "Handle edge case X", "Improve performance." Each iteration moves the output closer to production quality.

Step 5 — Automate

If you've done the same workflow twice, convert it to a script, a skill, or an automated pipeline. The loop compounds over time.

2.2 Example — Investigating a System Failure via Log Analysis

Consider a scenario where a backend run fails due to a routing issue. By opening the full workspace in the IDE — giving the agent access to all files, logs, and reports — rather than pasting only snippets, the agent can autonomously explore and cross-reference.

Pasting the relevant logs yields an agent analysis that identifies extreme congestion, elevated density, and blockage anomalies. Specifically, the agent detects that blockage area exceeds core size — a strong indicator of a floorplan error — and recommends targeted reports to confirm. In this case, that was exactly the root cause.

Value Delivered

A junior engineer diagnosed a complex failure independently, without waiting for a domain expert — saving hours of investigation time and eliminating a bottleneck.

2.3 Example — Automated Experiment Run Comparison

When comparing multiple experiment runs, an agent can automatically analyze metrics, generate HTML reports with charts and tables, compare runs side by side, and flag whether the comparison environment is valid (same configuration baseline, no environmental drift). It then produces actionable recommendations: which configuration showed the most significant improvement, which violations need investigation, and what next experiments to run.

This replaces a manual Excel comparison that would take hours — and produces a richer, more reproducible output.

CH 03

Multi-Agent Architecture

3.1 The Problem with a Single Agent on a Long Task

Assigning a single agent to a large, complex task produces two failure modes. First, the agent "fatigues" — output quality degrades over time as it begins to skip details or give shallow answers. Second, the context window fills up and the content is automatically compacted — and the agent is unaware this happened. It continues working as if nothing was lost.

Context compaction is silent. The agent does not know it has lost information. It continues with false confidence, often producing outputs that contradict earlier analysis.

This is not a bug — it is a fundamental property of how LLMs work. Design your workflows accordingly.

3.2 The Solution — Agent Pipelines with Defined Roles

Instead of one agent doing everything, build a pipeline of agents, each responsible for one stage. An example three-agent pipeline for complex technical analysis:

A1
Code Analysis
Understand logic flow & coverage path
A2
Environment Analysis
Relevant constraints & configs
A3
Stimulus Finding
Find triggering configuration

Each agent receives only the context it needs — nothing more — and passes its conclusions to the next. This keeps each individual task short, focused, and high-quality.

3.3 Why Multi-Agent Works

Advantages

  • Context isolation — each agent sees only what it needs, reducing hallucination
  • Reproducibility — any stage can be re-run independently
  • Controllability — validate each agent's output before proceeding
  • Quality preservation — each agent handles a short, focused task

Trade-offs

  • More upfront design work
  • Inter-agent communication overhead
  • Harder to debug cross-agent failures

3.4 Architecture Patterns

Orchestrator + Sub-Agents Pattern A

A primary orchestrator agent spawns and directs specialized sub-agents.

High automation, user-friendly
Extra abstraction layers reduce precision
Sub-agents may hit tool-call limits

Procedural Skills Pattern B

Each skill encodes a complete action sequence. The user can interactively steer mid-execution.

Dynamic and interactive
User can guide at each step
Less suitable for full automation

Atomic Skills Pattern C

Each skill performs exactly one operation. Maximum granularity and recomposability.

Maximum flexibility
Heavy context burden
Agent must choose action at every step
CH 04

Skills — When and How to Use Them

4.1 What Is a Skill

A skill is a pre-defined capability the agent can invoke. Instead of writing a long prompt every time you want a specific operation, you define a skill that wraps that operation — including the prompt, the required tools, and the expected output format. Think of it as a function you write once and call repeatedly.

An example production skill library might include: coverage investigation, code analysis, validity check, bug search, environment analysis, and stimulus finding. Each skill performs one focused operation and returns a structured result.

4.2 When to Use Skills

Recurring operations (2+ times) Consistent output format required Named stage in a pipeline

If you find yourself writing the same (or very similar) prompt more than twice, that's a signal to convert it into a skill. Skills also enforce output consistency — the agent won't improvise the structure every time.

4.3 When Not to Use Skills

One-off tasks: If it won't recur, don't invest time defining a skill. Use a regular prompt.

Exploratory work: When you don't yet know what you're looking for — investigating a new, unfamiliar bug type — work interactively. Skills are for tasks that have already crystallized into a repeatable pattern.

4.4 Critical Pitfall — Too Many Skills Creates Confusion

The agent selects skills based only on their name and description — it cannot see the skill content when choosing. With 100+ similar-sounding skills, it will frequently pick the wrong one.

Research confirms this: as the number of available skills grows, selection accuracy drops — especially when skills have semantic overlap. A well-maintained library of 10–20 skills consistently outperforms a sprawling collection of 100+.

The agent sees only the skill's identifier and description when making its selection. If you have skills with similar descriptions, the agent will guess — and guess wrong. Every skill must be semantically distinguishable from every other skill at the description level.

4.5 Best Practices for Skills

PracticeBad ExampleGood Example
Precise naming analyze analyze_routing_congestion_metrics
Narrow scope check_logs extract_blockage_violations_from_routing_log
Quantity limit 100+ skills in flat list 10–20 skills with clear hierarchy
Unique description "Analyzes data and finds issues" "Parses routing log and extracts congestion metrics per metal layer"
CH 05

Tools — Execution Capabilities

5.1 What Are Tools (in Agent Context)

Tools are execution capabilities the agent can invoke: file search, running shell commands, executing Python, calling APIs, querying databases. This is what transforms an LLM from a "smart chatbot" into an agent that actually does things. Without tools, the agent can only talk. With tools, it can search, run, analyze, and create.

5.2 The Central Rule — Execution ≠ Reasoning

One of the most common mistakes is asking the LLM to "think" about things that require precise computation. If you need to count log lines, calculate metric averages, or compare numbers — don't ask the agent to guess the answer. Ask it to run code that computes it.

Core Principle

Deterministic task (one right answer) → use a Tool. Judgment task (interpretation, explanation, ranking) → use LLM reasoning. Never conflate the two.

5.3 Tool Types and When to Use Each

Tool TypeUse ForWhen It's Essential
File / Repo Search Code exploration, module mapping, function location Entering an unfamiliar codebase
Code Execution Data parsing, numeric computation, chart generation Any task requiring an exact, reproducible answer
Log / File Search Pattern filtering, grep-like behavior, large file scanning Finding signals in high-volume output
System / CLI Test runs, build commands, deployment scripts End-to-end automation pipelines
External APIs (MCP) Live data access, regression databases, bug trackers Agent-initiated data retrieval without manual paste

5.4 Tool Pitfalls

Unconstrained tool access: Without clear constraints, agents run irrelevant operations or waste time. Always specify what the agent is and is not allowed to do.

LLM computing instead of executing: Never ask the agent to "calculate" — ask it to "run code that calculates." The difference is critical for accuracy.

Mixing reasoning and execution: The LLM decides what to do. The tool does it precisely. Blending these roles produces unreliable results.

CH 06

Markdown Files — The Agent's External Memory

6.1 Why This Is Critical

Agents remember nothing between sessions. Every new conversation starts from zero — the agent has no idea what you worked on yesterday, the conclusions from your last experiment, or the decisions already made. And even within a session, context compaction silently erases information mid-stream.

The solution: Markdown files that persist your "memory" outside the agent. Write them at the end of each session, load them at the start of the next. This transforms the agent from a one-off conversation into a continuous assistant with accumulated context.

6.2 Recommended Markdown File Types

FileContentsUpdate Frequency
project_context.md Project description, constraints, architecture, tooling, key metrics Rarely — foundational context
debug_notes.md Bugs found, patterns identified, lessons learned Every session with findings
experiments.md Run log — parameters, results, conclusions Every experiment run
decisions.md Why approach X over Y, trade-offs, approvals Every architectural decision
session_summary.md What was done, findings, decisions, next steps End of every session

6.3 Workflow Integration

Session Start — Load Context

Please read these files for context:
- project_context.md
- session_summary.md
- experiments.md

Continue the analysis from where we left off.

Session End — Persist State

Summarize today's session in Markdown format for session_summary.md.
Include:
- Key findings
- Decisions made and rationale
- Open questions
- Next steps

Analysis Input — Markdown as Data

Based on experiments.md, which hyperparameter combination showed
the best convergence? Suggest the next 3 experiments to run,
building on what has already been tried.

6.4 Advanced Pattern — Stateful Agent via Markdown

Treat Markdown files as the agent's state object. Each session: load state → work → write updated state. This simulates a long-running agent with persistent memory, even though each session is technically fresh.

Session Input:
  ├── current_task/  (logs, code, data)
  ├── session_summary.md  (what we know)
  └── experiments.md  (what we've tried)

→ Agent works with full continuity

Session Output:
  ├── Updated session_summary.md
  └── Updated experiments.mdPATTERN
CH 07

Validation — Why and How

7.1 The Problem — False Confidence

This may be the single most important point in the entire guide. Agents sometimes fabricate logic or explanations that sound correct but are not grounded in reality — especially when no domain expert is immediately available to cross-check.

The agent does not say "I'm not sure." It presents its answer with full confidence — even when it's wrong. This creates an illusion of correctness that can lead to costly engineering decisions built on false premises.

7.2 The Hybrid Approach

The most effective validation strategy combines deterministic code (which generates exact reports and checks environmental sanity) with agent analysis (which provides insights and explanations). The deterministic layer serves as an anchor — if the agent's output contradicts what the traditional tools show, you know to investigate further.

7.3 Four Validation Levels

1
Sanity
Does it run? No crash? Output looks plausible? Takes seconds, catches gross errors.
2
Correctness
Run against known data, compare to expected output. Requires ground truth.
3
Edge Cases
Null inputs, negative numbers, empty strings, boundary values. Agents skip these most often.
4
Production
Performance at scale, failure modes, race conditions, API unavailability.

7.4 The Golden Rule

If you cannot verify the output → do not trust it.

The agent is fast. You are precise. This combination works only if the validation step is never skipped.

CH 08

Work Environment — Setup That Makes a Difference

8.1 Why Full Workspace Access Is Critical

Opening the full workspace in the IDE — so the agent has access to all files, logs, configs, and reports — fundamentally changes the quality of analysis. When the agent sees only a pasted snippet, it works with partial information. When it sees the entire workspace, it can explore independently, cross-reference files, and surface deeper insights.

This is often the single biggest "unlock" available to teams that are underutilizing agents.

8.2 Recommended Setup

  • IDE + AI Copilot on your development or experiment machine — including remote SSH connections
  • All logs, configs, and scripts accessible within the workspace — not just source code
  • CLI agent (e.g., Claude Code) for tasks requiring command execution or long pipelines
  • Markdown memory files in the repository root (as described in Chapter 6)

8.3 Work Modes

ModeWhen to UseExample
Chat Quick questions, explanations, initial exploration "What does this function do?"
Agent Mode Multi-step workflows, deep analysis, code generation "Investigate this failure end-to-end"
CLI / Terminal Automation, script execution, pipelines "Run comparison script on 3 experiment runs"

Prompt Engineering — How to Direct an Agent

9.1 The Foundational Rule

Garbage prompt → garbage output.

The gap between a good and a bad prompt is not a marginal improvement — it is the difference between a useful result and wasted time.

9.2 Pattern — Investigation / Failure Analysis

Analyze the following logs:
[paste logs or reference file path]

Focus on:
- Primary failure cause (with evidence from the log)
- Secondary contributing factors
- Whether environment or configuration issues could be involved

Output:
- Structured explanation of the failure chain
- Top 3 hypotheses, ranked by likelihood
- For each hypothesis: evidence that supports it, and what
  test would confirm or deny itPROMPT TEMPLATE

9.3 Pattern — Experiment Run Comparison

Compare these experiment runs:
[run1 details]
[run2 details]

Output:
- Table of key metric comparisons
- Which run is better overall and why
- Trade-offs (where run1 wins, where run2 wins)
- Recommendations for next experiments
- Confirm comparison validity (same baseline environment and config)PROMPT TEMPLATE

9.4 Pattern — Code Writing

Write a Python function that:
- Input:  [describe input format and type]
- Output: [describe output format and type]
- Constraints: [edge cases, performance requirements, limits]

Also include:
- Type hints and docstring
- Unit tests covering: normal case + at least 2 edge cases
- Error handling for invalid inputPROMPT TEMPLATE

9.5 Pattern — Anti-Hallucination / Iterative Refinement

Double-check your previous answer:
- What assumptions did you make? Are they valid given the data?
- What could be wrong with your analysis?
- Is there an alternative explanation you didn't consider?
- How would you validate your conclusions?PROMPT TEMPLATE

This pattern is critical. It forces the agent to pause and stress-test its own reasoning rather than confidently proceeding on flawed premises. Use it whenever the stakes of an incorrect answer are high.

9.6 Pattern — The Rubber Duck Agent

Classic rubber-duck debugging says: explain your problem to a rubber duck, and the act of articulating it reveals the answer. The agent version inverts the trick — the agent is the duck, but a duck that asks back.

Spin up a dedicated agent whose only job is to interrogate you, not to write code or produce a solution. It probes assumptions, asks for missing context, and reflects your reasoning back at you until the real problem is exposed. By the time you finish answering, the next step is usually obvious — and your prompt to the executing agent is now sharp enough to actually work.

You are my Rubber Duck Agent. You do NOT write code,
propose solutions, or take actions.

Your only job:
- Ask me clarifying questions, one at a time
- Challenge my assumptions and surface what I'm taking for granted
- Reflect my reasoning back to me in your own words
- Point out gaps, contradictions, or missing context
- Keep asking until the real problem (not the symptom) is clear

Topic I want to think through:
[describe the problem, bug, design decision, or stuck point]

Begin with the single most important question.PROMPT TEMPLATE

When to use it: stuck on a bug, unsure how to scope a task, before writing a big prompt for an executing agent, or any time you catch yourself typing a wall of context and realizing you don't actually understand the problem yet.

Pipeline tip: pair it with your executing agent. Duck first to sharpen the question, then hand the refined problem statement to the agent that actually does the work. The two-agent split — thinker and doer — consistently beats a single agent trying to do both.

CH 10

Context Management — Working Within Limits

10.1 The Problem

Every agent operates within a finite context window. When it fills, one of two things happens: the agent refuses further input, or the content is compacted automatically. The compaction problem is insidious — the agent doesn't know it lost information and continues working as if everything is intact.

A context compaction event (e.g., 54,000 tokens compressed to 24,000) can happen externally, triggered by the platform — not by the agent itself. The agent has no awareness of the event.

10.2 Mitigation Strategies

Work in Chunks

Instead of pasting 10,000 lines of logs at once, split into chunks and analyze each independently. Merge conclusions at the end.

Re-anchor Key Context Periodically

In long sessions, periodically re-state the most important facts. Don't assume the agent remembers what you said 20 messages ago.

Persist Intermediate Results

Every time the agent reaches an important conclusion, save it to an external file. If context is truncated, you have a backup.

Use Multi-Agent Design

Instead of one long session, split into short sessions with separate agents — each receiving only what it needs. This is the architectural solution to context limits.

CH 11

Evaluation — Knowing Your Agent Is Actually Working

11.1 Why Systematic Evaluation Is Non-Negotiable

If you are building workflows based on agents, you must know whether they actually work. "It feels like it's working" is not a measurement. You need metrics — especially before deploying a skill or pipeline to other users.

Build dedicated evaluators for each skill, using a mix of synthetic data (files injected with known issues) and real-world examples from actual use cases.

11.2 Recommended Metrics

🎯
Precision
What fraction of the agent's answers were correct?
📡
Recall
What fraction of the correct answers did the agent find?
⚡
Tool Call Count
Is the agent working efficiently, or wasting calls?
⏱
Execution Time
How long does each task take end-to-end?
👥
User Feedback
Did it help? Did it surface issues the user didn't know existed?
🔁
Regression Rate
Does improving one skill degrade another?

11.3 Improving Prompts — The Feedback Loop

Prompt improvement is currently manual in most teams: change a prompt, run the evaluation suite, check whether metrics improved. The long-term goal is to automate this loop — scripts that collect agent usage data, identify prompt failures, and suggest targeted improvements. This transforms prompt engineering from artisanal to systematic.

CH 13

What's Next — Self-Improvement Loops and MCP

13.1 The Self-Improvement Loop

The next frontier in agentic workflows is using the agent to improve the agent. Recurring exploration and feedback loops — where the agent identifies patterns in its own failures or in user interactions — can be converted into feature improvements, better prompts, or new skills with the help of the same AI infrastructure. This closes the loop: the agent gets better at its domain as you use it.

13.2 MCP — Model Context Protocol

The emerging standard for connecting agents to live data sources is the Model Context Protocol (MCP). Rather than the user manually pasting data into the agent, the agent connects directly to regression databases, experiment runners, bug trackers, and dashboards — and pulls the data it needs autonomously.

Paradigm Shift

From "I bring data to the agent" → to "the agent goes to the data itself." MCP makes agents first-class citizens in your data infrastructure.

MCP-connected agents can autonomously query live experiment results, cross-reference multiple data sources, and produce analyses that would previously require manual data assembly — removing one of the biggest remaining friction points in agent-assisted engineering workflows.
